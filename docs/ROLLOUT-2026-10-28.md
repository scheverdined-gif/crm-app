# Установка обновления: SQL сначала, Merge после проверки

## Обязательное условие Merge

**Не нажимать Merge pull request / Confirm merge до проверки резервной копии, применения новой SQL-миграции и её контрольной проверки.** Vercel может автоматически развернуть `main` сразу после слияния. Никаких миграций в команде сборки нет и не добавлено.

До миграции новая версия безопасно отклоняет удаление, включая одиночное, и показывает, какой SQL требуется. Она не выполняет обходных одиночных удалений, если серия не удалилась. Темы, календарь, вход, создание и проведение продолжают работать. Тем не менее новая функция удаления до миграции недоступна, поэтому порядок «сначала Merge, SQL когда-нибудь потом» для готового выпуска не подходит.

## Что перенесено и с чем сравнивали

Исходный `main`: `c09527ae24d88f70b2579f51c57f5add4532671e`. Его существующие `App.jsx` и оба затрагиваемых файла адаптера побайтово совпали с базой локального проверенного обновления; три небольших UI-модуля добавляются. Существующие файлы не удаляются.

- `src/App.jsx`, `src/calendar.js`, `src/theme.js`, `src/series.js`: переключение темы, локальная текущая дата и диалог областей удаления с точным количеством.
- `src/storage/model.js`, `src/storage/supabase.js`: передача подтверждённых ID, замороженных версий и вызов одной атомарной функции `crm_delete_session_scope`. Пропуск `phone` сохранён из подготовленного обновления; новая форма телефона не добавлялась.
- `supabase/migrations/2026102801_safe_series_delete.sql`: единственная новая рабочая миграция. Добавляет функцию и защитный триггер без изменения/удаления записей, старых политик RLS и Auth.
- `supabase/CHECK-20261028-READ-ONLY.sql`: запросы проверки, только чтение.
- `tests/`, два браузерных сценария в `scripts/`, эта инструкция и отчёт — проверки и установка.

`scripts/build.mjs`, остальные прежние скрипты, `package.json`, `package-lock.json`, `vite.config.js`, `supabase.public.json`, `src/main.jsx`, расчётный `src/crmLogic.js` и Auth-хук `src/storage/useRemoteSchool.js` остаются без изменений. Зависимости не добавлялись. `vercel.json` в исходном репозитории отсутствует; он не создаётся. Настройки панели Vercel в этой работе не менялись и не проверялись. Секреты, `.env.local`, сборка `dist`, локальные кэши и пользовательские данные в коммит не входят.

Серии связываются исключительно существующим `template_id`. Записи без него не объединяются по названию. Удалять можно только непроведённые занятия без записанных отметок/результатов и источника конверсии; проведённые и пропущенные занятия сохраняются. Ставки и правила промо остаются прежними. Администратору не даются кнопки записи; роль и права дополнительно проверяет сервер.

## Безопасный порядок для существующего Supabase

1. Проверить идентичность существующего проекта. Убедиться, что резервная копия данных и определений схемы доступна и понятно, как её восстановить; само наличие файла SQL не заменяет проверенную резервную копию. При необходимости сохранить дамп существующих определений затрагиваемых функций/триггеров. На время применения остановить новые записи и согласовать короткое окно обновления.
2. Выполнить по одному SELECT из `supabase/CHECK-20261028-READ-ONLY.sql`. Сохранить количества записей, список политик и прав. До миграции новой функции и триггера может не быть — это ожидаемо. Проверить, что установлен прежний Stage 1 с `crm_mutate`, `crm_private.checked_row` и полями `template_id`, `revision`, `attendance_recorded`, `promo_result`, `promo_conversion_session_id`. При отличающейся схеме сначала проверить совместимость; ничего не очищать.
3. Просмотреть diff **единственного** рабочего SQL `supabase/migrations/2026102801_safe_series_delete.sql`. Выполнить его целиком от BEGIN до COMMIT в SQL Editor существующего проекта. Файл создаёт функцию/триггер, но не импортирует и не удаляет записи. Старые миграции и CSV-импорт не запускать. Не отключать RLS, не создавать новую базу и не менять ключи/аккаунты.
4. Дождаться успеха и повторить SELECT-проверки. Количества записей и прежние RLS должны остаться прежними. Ожидаются включённый `crm_keep_training_history` и новая публичная функция с EXECUTE для `authenticated`, без EXECUTE для `anon`. Миграция уведомляет API об обновлении схемы.
5. По отдельному согласованию проверить на искусственной серии в существующем проекте и разрешённом preview: владелец/свой наставник удаляет непроведённые занятия с показанным количеством; чужой наставник и администратор не могут это сделать; проведённое/пропущенное, отметки и начисления сохраняются. Реальные серии для такого теста не использовать. При несовпадении количества/версии операция должна целиком отклониться. Старый клиент может по-прежнему создавать/проводить занятия и удалять чистое непроведённое; удаление истории теперь запрещено триггером намеренно.
6. Только после шагов выше нажать **Merge pull request → Confirm merge**. Дождаться сборки Vercel и проверить вход, обе темы, календарь и ограниченные роли. Обновить открытые вкладки CRM. `.env.local` локального приложения не заменять.

Если миграция завершается ошибкой — остановиться, сохранить сообщение, выполнить ROLLBACK, если редактор оставил прерванную транзакцию, и проверить причину. Не повторять старые миграции и не расширять права ради обхода ошибки.

Если после Merge возникнет проблема интерфейса, можно откатить фронтенд-коммит. Это не повод снимать защитный триггер, отключать RLS или удалять данные. Возврат изменений SQL и любые операции с историческими занятиями требуют отдельного согласованного плана.

## Где находятся старые SQL

`tests/fixtures/legacy-schema/` — **не миграции установки**, а исходная схема для изолированных PGlite-тестов. Не применять эти файлы к Supabase. Браузерные проверки также поднимают только локальный HTTP-стенд и PGlite; рабочая база в них не используется.

## Воспроизведение проверок

После обычной установки зависимостей по существующему lockfile:

```sh
npm test
npm run build
```

Браузерные проверки используют Playwright из уже имеющихся devDependencies. Если локальный Chromium ещё не установлен, на macOS/Linux:

```sh
PLAYWRIGHT_BROWSERS_PATH=.playwright-browsers npx playwright install chromium --only-shell
```

На Windows PowerShell перед такой установкой задать `$env:PLAYWRIGHT_BROWSERS_PATH=".playwright-browsers"`, затем выполнить `npx playwright install chromium --only-shell`. После установки:

```sh
node scripts/browser-check.mjs
node scripts/check-three-features.mjs
```

Оба сценария явно подменяют конфигурацию API на локальный адрес; реальные ключи или аккаунты не нужны. Не менять их на рабочие URL ради проверки.
